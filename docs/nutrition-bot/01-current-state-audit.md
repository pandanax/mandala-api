# Аудит текущей архитектуры перед добавлением `nutrition`

Дата аудита: 30 августа 2026 года. Основа: `main` на коммите `49106fa`.

## Краткий вывод

Репозиторий уже содержит правильный фундамент «одно ядро — несколько вертикалей»:
`InboundEvent.vertical_id`, изолированные пользователи и профили, раздельные Telegram-токены,
per-vertical LLM-конфигурацию и фильтрацию RAG. Поэтому второй бот не требует второго приложения
или копирования кодовой базы.

При этом продуктовый слой не полностью multi-tenant. Если сейчас только добавить токен и строку
`nutrition` в БД, пользователь второго бота сможет попасть в астрологические команды и настройки,
а Telegram burger menu для него корректно не зарегистрируется. До запуска нужна небольшая, но
принципиальная декомпозиция конфигурации вертикалей.

## Что уже можно переиспользовать

| Контур | Текущее состояние | Вывод для `nutrition` |
|---|---|---|
| Идентификация | Пользователь создаётся по `(vertical_id, channel, external_user_id)` | Один Telegram user получает разные `user_id` и профили в двух ботах |
| OLTP | `users`, `channel_links`, `client_profiles`, `messages`, платежи содержат `vertical_id`; FK ведёт в `agent_verticals` | Общую БД использовать безопасно после добавления seed/migration |
| Telegram token map | `load_bot_token_map()` поддерживает `TELEGRAM_BOT_TOKEN_<VERTICAL>` и JSON map | Можно держать два токена в одном процессе |
| Webhook | URL `/webhooks/telegram/{vertical_id}`, исходящий токен выбирается по vertical | Для второго бота нужен отдельный webhook URL |
| Polling | `run_polling_multi()` запускает поток на каждый token/vertical | Локальная и аварийная проверка двух ботов уже возможна |
| LLM | Модель разрешается через `LlmConfigProvider.resolve(vertical_id)` | Можно задать `LLM_MODEL_NUTRITION` независимо от astrology |
| Intake | Шаги загружаются из `intake_steps.json` по vertical | Новый сценарий добавляется данными плюс новыми валидаторами |
| RAG | Каталог `kb/{vertical_id}` и Qdrant payload фильтруются по vertical | Нутрициологическая KB не смешивается с астрологической |
| Квота и Stars | Баланс, платежи и сообщения идут с `vertical_id` | Текущую коммерческую механику можно переиспользовать |
| Диалог | История извлекается в рамках user/vertical | Контекст двух ботов не смешивается |

## Найденные границы и риски

### P0 — исправить до появления токена `nutrition`

1. **Команды Telegram не per-vertical.** `bot_commands.py` содержит один астрологический
   `BOT_COMMANDS` и на старте читает только legacy-пару `TELEGRAM_BOT_TOKEN` +
   `TELEGRAM_VERTICAL_ID`. Multi-token map уже существует, но `setMyCommands` его не использует.

2. **Астрологические команды распознаются общим intake-кодом.** В `scenario_intake.py`
   `/natal`, `/matrix` и `/numerology` входят в общий `_ALL_COMMANDS`, а обработчик не проверяет
   `event.vertical_id` перед запуском расчётов/рендеров. После добавления intake для nutrition
   эти команды станут доступны во втором боте.

3. **Утренняя астрологическая рассылка маршрутизируется глобально.** `/morning` и
   `mdl:morning*` перехватываются в `domain/handler.py` до intake без проверки vertical.
   Планировщик проходит по всем токенам; репозиторий сейчас выбирает только профили с
   `birth_date`, что случайно ограничивает рассылку, но не является безопасной продуктовой
   границей.

4. **Webhook secret общий для всех ботов.** Один `TELEGRAM_WEBHOOK_SECRET` технически работает,
   но компрометация одного секрета затрагивает оба webhook. Нужен резолвер
   `TELEGRAM_WEBHOOK_SECRET_<VERTICAL>` с legacy fallback и проверка, что vertical из URL
   существует в token map. Иначе произвольный slug доходит до доменного слоя.

5. **Неизвестная вертикаль получает default prompt.** `get_vertical_system_prompt()` не
   fail-closed. Для production Telegram-входа конфигурация должна валидироваться на старте,
   а неизвестный/неактивный vertical отклоняться до создания пользователя.

### P1 — сделать частью конфигурации продукта

1. `quick_actions.py`, `nav_guarantee.py`, приветствия, help, post-intake offer и profile render
   реализованы через `if vertical == ...`. Добавление третьего набора продолжит разрастание
   условных веток. Нужен типизированный `VerticalDefinition`, остающийся в коде и тестируемый,
   а не произвольный JSON из БД.

2. Общий `profile_view.py` знает только поля рождения. Для nutrition нужен отдельный безопасный
   рендер профиля: цель, ограничения, предпочтения и режим — без вывода чувствительных данных,
   которые не нужны пользователю в каждом просмотре.

3. `client_knowledge.py` глобально разрешает LLM-хвост `natal_chart_text`. Модель nutrition не
   должна иметь возможность писать астрологические ключи. Разрешённые ключи должны определяться
   vertical-конфигурацией; предпочтительно вообще не позволять nutrition записывать профиль из
   свободного ответа LLM.

4. `post_intake_intent()` общий и может отправить запрос в генерацию изображений. Для nutrition
   генерация изображений не является MVP-функцией и должна быть явно выключена capability-флагом.

5. `_COMMANDS_HELP`, `/help`, `/profile`, `/start` и fallback navigation сейчас имеют
   астрологические или demo-тексты. Для nutrition нужны собственные детерминированные варианты.

6. Миграция seed содержит только `astrology` и `therapy`. Нельзя менять старую применённую
   миграцию; требуется новая Alembic revision с идемпотентным добавлением `nutrition`.

### P2 — эксплуатационная зрелость

1. Startup health сообщает только состояние БД. Нужна диагностика зарегистрированных вертикалей:
   без вывода секретов логировать token map, effective LLM model, наличие prompt/intake/commands
   и статус RAG index.
2. Текущий deploy smoke отправляет web-запрос только в `astrology`. Следует оставить его без
   изменений и добавить отдельный nutrition smoke, чтобы сбой второго бота не маскировался общим
   `/health`.
3. Нет продуктовых метрик в разрезе сценариев nutrition: завершение intake, safety-escalation,
   запрос меню, принятие цели, недельный check-in. Все метрики должны включать `vertical_id` и не
   содержать текст пользователя, вес, диагнозы или иные чувствительные значения.

## Что обнаружено про NITN/n8n

В отслеживаемых файлах нет Python/JavaScript-реализации старого нутрициологического бота и нет
экспортов n8n workflow. Найдены только инфраструктурные упоминания n8n:

- VM `n8n-server`, Managed PostgreSQL `n8n-postgres` и сеть в Yandex Cloud;
- nginx/certbot, через которые уже опубликован Mandala API;
- инструкции, явно отделяющие контейнер `mandala-http` от n8n.

Их удаление сломает или сделает неуправляемым production-контур астролога. Поэтому очистка
делается только после внешнего инвентаризационного шага:

1. В n8n UI/API найти workflow старого nutrition-бота по Telegram credential/webhook URL.
2. Проверить последние executions, активность webhook и владельца credential.
3. Экспортировать workflow и список credential metadata в защищённый архив без секретов в Git.
4. Отключить workflow, выдержать согласованное окно наблюдения, проверить отсутствие трафика.
5. Только затем удалить workflow/credential/webhook старого бота. VM, nginx, certbot, сеть и
   PostgreSQL-кластер не удалять в рамках этой задачи.

Этот внешний cleanup — отдельная production-операция с подтверждением пользователя; он не нужен
для разработки новой Python-вертикали.
